## 7. 목표 미달 · 정산 (F-11, F-12)

### 7.1 펀딩 종료 결과 · 목표 미달 처리 (UI-22, UI-23, API S1)

**1) 규칙 · 흐름**
- 종료된 펀딩에서 선물별 목표 금액 · 실제 모금액 · 달성 여부를 보여준다.
- 목표를 달성한 선물 → 정상 정산 대상.
- 목표 미달 선물(모금액 > 0) → 생일자가 **둘 중 하나**를 고른다:
  1. 다음 생일로 이월 → 이월 기록(📌 다음 생일에 펀딩을 다시 연다, 5.5)
  2. 현재 모금액 인출 → 정산 대상
- 선택 → 최종 확인 모달 → 처리. **처리 후에는 바꿀 수 없다.** 같은 금액을 이월과 인출에 중복 사용할 수 없다.
- 개인 자금을 플랫폼 안에서 추가로 내는 기능은 없다. 인출한 돈에 보태 직접 구매한다.

**2) 입력 · 결과**: `{ action: "carryover" | "withdraw" }` → `204`

**3) 검증**

| 조건 | 결과 | 위치 |
|---|---|---|
| 펀딩이 종료되지 않음 | `409 FUNDING_NOT_ACTIVE` "펀딩이 종료된 후에 처리할 수 있어요." | ✅ 프론트(안내) ✅ Mock |
| 목표 달성 선물 | `400` "목표를 달성한 선물은 정상 정산 대상이에요." | ✅ Mock |
| 모금액 0원 📌 Q14 | 미달 처리 대상이 아니다. 화면에 **"종료됨"**으로 표시하고 끝난다 (이월 · 인출 · 정산 없음). 처리 요청이 오면 `400` "모금액이 없어 처리할 금액이 없어요." | ✅ Mock(요청 거절) · ✅ 프론트("종료됨" 배지) |
| 0원 선물 판단 방식 📌 | `shortfall_action`은 NULL 그대로 두고 새 값을 저장하지 않는다. "종료 + 모금액 0원"이면 미달 처리 · 미달 안내 · 정산 · 7일 알림 대상에서 **계산으로 제외**한다 (2026-10-19 확정) | ✅ Mock · ✅ 프론트 |
| 이미 처리함 | `409` "이미 처리한 선물이에요. 같은 금액을 다시 처리할 수 없어요." | ✅ Mock |
| 생일자 아님 | `403` | ✅ Mock |

**5) 데이터 · API**: `gifts.shortfall_action`, `carryovers` · `POST /gifts/{id}/shortfall`

**6) FastAPI 구현 항목** 🔧: 선물 행 잠금 후 상태 확인, 이월 기록 생성과 선물 상태 변경을 한 트랜잭션, `carryovers.gift_id` UNIQUE

📌 **확정 (Q12)**: 미달 선물의 이월 / 인출 선택 기한은 **펀딩 종료 후 7일**이다. 7일이 지나도 고르지 않은 선물이 있으면 생일자에게 **다시 알림**을 보낸다. 알림이 간 뒤에도 생일자는 계속 고를 수 있다(자동으로 정하지 않음).
- 🔧 백엔드: 매일 도는 알림 작업(8.2)이 "종료일 + 7일이 지났고 처리하지 않은 미달 선물(모금액 > 0)"이 있는 펀딩을 찾아 생일자에게 `shortfall-reminder` 알림을 만든다. 알림을 누르면 목표 미달 처리 화면(UI-23)으로 간다.
- ✅ 화면(UI-23 기한 안내 · 지나면 경고, 알림 목록 "미달 처리" 배지) · ✅ Mock(알림 조회 시 생성, 펀딩당 1회)
- 📌 **확정 (Q12-1)**: 7일 경과 알림은 **한 번만** 보낸다. (중복 방지 키: 선물 단위가 아니라 펀딩 단위 1회 — `dedupe_key = 펀딩ID:shortfall-reminder`)

### 7.2 정산 관리 (UI-24, API S2 · S3)

**1) 규칙 · 흐름**
- 생일자만 이용한다. 후원자에게는 정산 정보를 주지 않는다.
- 정산 대상 = 종료된 펀딩의 (목표 달성 선물 + 인출을 선택한 미달 선물) − 이미 정산 요청한 선물. 이월한 선물은 제외.
- 📌 "이미 정산 요청한 선물" = `requested` · `processing` · `completed` 정산에 들어간 선물. 이력이 없거나 `failed` 정산에만 있는 선물만 요청할 수 있다. 처리 중에 같은 선물로 다시 요청하거나 동시에 두 번 요청해도 선물 행 잠금 + 부분 UNIQUE로 하나만 저장된다 (2026-10-19 명시)
- 정산할 선물을 고르고(기본: 전부 선택) 은행 · 계좌번호 · 예금주를 입력해 요청한다.
- **예금주는 본인 명의**여야 한다. (DEFINITION 8장)
- 정산 금액은 서버가 선물별 모금액으로 계산한다. 요청한 선물은 다시 정산할 수 없다.
- 정산 상태 · 이력을 보여준다. 실제 송금 없는 **모의 정산**이다(화면에 표시). ✅ 프론트

**2) 입력 · 결과**: `{ gift_ids[], bank, account_number, account_holder }` → `201 { id }` · 현황 `SettlementOverviewDto`(계좌번호는 마스킹)

**3) 검증**

| 항목 | 조건 | 문구 | 위치 |
|---|---|---|---|
| 은행 | 미선택 | 은행을 선택해 주세요. | ✅ 프론트 ✅ Mock · 📌 9개 은행 (Q10) |
| 계좌번호 | 비어 있음 / 형식 | 계좌번호를 입력해 주세요. / 계좌번호는 숫자 10~14자리로 입력해 주세요. | ✅ 프론트 ✅ Mock · 📌 숫자 10~14자리 (Q10) |
| 예금주 | 비어 있음 / 본인 이름과 다름 | 예금주를 입력해 주세요. / 본인 명의 계좌만 등록할 수 있어요. | ✅ 프론트 ✅ Mock · 📌 회원 이름과 비교 (Q10) |
| 선물 | 0개 / 정산 불가 선물 / 이미 정산 | 정산할 선물을 선택해 주세요. / 정산할 수 없는 선물이 포함되어 있어요. / 이미 정산 요청한 선물이 포함되어 있어요. | ✅ Mock |
| 펀딩 | 종료 전 | 펀딩이 종료된 후에 처리할 수 있어요. | ✅ Mock |
| 이전 정산 실패 📌 | 실패한 정산의 선물 | 다시 정산 대상 (재요청 가능) | ✅ 프론트 ✅ Mock |

**4) 예외**: 정산 가능 금액 없음 → 요청 버튼 비활성 · 중복 요청 `409` · 실패 시 상태 · 오류 안내

**5) 데이터 · API**: `settlements`, `settlement_items` · `GET /fundings/{id}/settlement`, `POST /fundings/{id}/settlements`

**6) FastAPI 구현 항목** 🔧
- 선물 행 잠금 → 정산 가능 여부 · 금액 계산 → `settlements` + `settlement_items` 저장을 한 트랜잭션
- 실패(`failed`)가 아닌 정산에 같은 선물 중복 금지(부분 UNIQUE 인덱스)
- 계좌번호 암호화 저장 (📌 Fernet + `.env`의 `ACCOUNT_ENCRYPTION_KEY`, 2026-10-19 확정), 응답 마스킹

📌 **확정 (Q11)**: 정산 상태는 사람이 바꾸지 않고 **프로그램이 정산 처리 결과에 따라 자동으로** 바꾼다. `requested`(요청 접수) → `processing`(처리 시작) → `completed`(송금 완료) 또는 `failed`(송금 실패). 🔧 백엔드: 정산 처리 작업(스케줄러 또는 송금 연동 결과 수신)이 상태와 `processed_at` · `failure_reason`을 기록한다. (✅ Mock: 요청 3초 뒤 "처리 중", 8초 뒤 "완료" 또는 "실패"로 흉내 냄 — 실제 시점은 백엔드에서 정함)

📌 **확정 (Q11-1 ②)**: 정산이 **실패**하면 실패 이유를 보여주고 **계좌 정보를 다시 입력해 재요청**할 수 있다.

| 실패 이유 (`failure_reason`) | 화면 문구 | 다음 동작 |
|---|---|---|
| `ACCOUNT_INVALID` 계좌 정보 오류 | 계좌 정보가 올바르지 않습니다. 계좌 정보를 다시 입력해 주세요. | 은행 · 계좌번호 · 예금주를 다시 입력해 재요청 |
| `BANK_ERROR` 은행 오류 | 은행 오류입니다. 다시 입력해 주세요. | 계좌 정보를 다시 입력해 재요청 |

- 실패한 정산에 포함된 선물은 다시 **정산 대상**이 된다. ("실패가 아닌 정산에 같은 선물 중복 금지" 규칙과 맞음, 6.2.5 부분 UNIQUE)
- 실패한 정산 기록은 이력에 그대로 남긴다(실패 이유 포함).
- 🔧 백엔드: 송금 결과에 따라 `failed` + `failure_reason` 기록 → 정산 현황 응답에 실패 이유 포함 → 그 선물을 정산 가능 목록에 다시 넣는다.
- ✅ 화면: 최근 정산이 실패하면 맨 위에 이유 안내, 이력에도 이유 표시, 처리 중에는 3초마다 자동 새로고침 · ✅ Mock(모의 진행 규칙은 백엔드에서 실제 송금 결과로 대체)

📌 **확정 (Q11-1 ①, 2026-10-19)**: 모의 정산은 요청 **즉시 "처리 중"**, **1분 뒤 "완료"**(실패 확인용 계좌는 "실패")로 바뀐다. ✅ Mock 반영

### 7.3 정산 상태 표시 — 종료된 펀딩 화면 (UI-12, UI-22, 내 펀딩 목록)

📌 **확정 (2026-10-16 사용자 요청)**: 정산이 끝나면 종료된 펀딩 화면에 **"정산됨"**을 표시한다.

**1) 규칙 · 흐름**
- 선물마다 자기가 들어간 정산의 상태를 응답에 담는다. 화면은 그 값으로 배지를 고른다.
- 정산 대상 선물 = 모금액이 있고, 목표를 달성했거나 "현재 모금액 인출"을 고른 선물. 이월한 선물과 0원 선물은 대상이 아니다.

| 단위 | 조건 | 표시 | 보이는 곳 |
|---|---|---|---|
| 선물 | 정산 `completed` | **정산됨** | 종료 결과(UI-22) · 목표 미달 처리(UI-23) · 내 펀딩 관리(UI-12) 선물 카드 |
| 선물 | 정산 `requested` · `processing` | 정산 진행 중 | 종료 결과 · 목표 미달 처리 |
| 선물 | 정산 `failed` | 정산 전 배지로 돌아감 (다시 정산 대상, 7.2) | — |
| 펀딩 | 정산 대상 선물이 **모두** `completed` | **정산됨** | 내 펀딩 목록 카드 · 내 펀딩 관리 · 종료 결과 |
| 펀딩 | 대상 중 하나라도 `requested` · `processing` | 정산 진행 중 | 같음 |
| 펀딩 | 일부만 `completed`, 나머지는 정산 전 | 일부 정산됨 | 같음 |
| 펀딩 | 진행 중 · 예정 펀딩, 정산 전, 대상 없음 | 표시 없음 | — |

- "정산 진행 중" · "일부 정산됨"은 상태를 그대로 보여주는 **화면 표시 방식**이다(정책 변경 아님). 바꾸려면 화면 배지만 고치면 된다.
- 후원자 화면(친구 펀딩)에는 정산 정보를 보여주지 않는다(7.2 · F-13).

**2) 입력 · 결과**: 입력 없음. `OwnerGiftDto.settlement_status: "requested" | "processing" | "completed" | "failed" | null` (API_SPEC 3.3). 펀딩 단위 표시는 응답의 선물 목록으로 프론트가 계산한다.

**3) 검증**: 생일자 본인 펀딩 응답(`OwnerFundingDto`)에만 넣는다. `FriendFundingDto`에는 넣지 않는다.

**4) 예외**: 상태가 바뀌는 도중 화면은 이전 값을 보일 수 있다 → 다시 조회하면 최신 값. 정산 관리 화면은 진행 중일 때 3초마다 다시 조회한다.

**5) 데이터 · API**: `settlement_items`(선물 ↔ 정산) → `settlements.status` (실패하지 않은 정산, DATA_MODEL 6.2.5) — Mock은 `DbGift.settlementId`로 대신함 · `GET /me/fundings` (F1), `GET /me/fundings/{funding_id}` (F2)

**6) FastAPI 구현 항목** 🔧
- 내 펀딩 조회 시 선물별로 "실패가 아닌 가장 최근 정산"의 상태를 함께 조회해 `settlement_status`로 내려준다 (선물 수만큼 따로 조회하지 않도록 JOIN 또는 한 번에 묶어 조회).
- 실패하면 `null`(다시 정산 대상)로 보이게 한다.

**현재 구현**: ✅ 프론트(선물 · 펀딩 배지 3곳) · ✅ Mock(응답에 `settlementStatus` 포함, 조회할 때 모의 정산 상태를 먼저 진행시킴)
