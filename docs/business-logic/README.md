## 0. 읽는 법

### 0.1 구현 위치 표시

| 표시 | 뜻 |
|---|---|
| ✅ **프론트** | 프론트엔드 화면에 이미 구현됨 (입력 형식 안내, 버튼 잠금, 표시 계산 등) |
| ✅ **Mock** | 프론트의 Mock 서버(`frontend/src/lib/mock/handlers/*`)에 임시로 구현됨 — **백엔드가 같은 규칙으로 다시 구현해야 함** |
| 🔧 **백엔드** | 아직 없음. FastAPI에서 새로 구현해야 함 (트랜잭션, 잠금, 암호화, 스케줄러 등) |
| ❓ **확인 필요** | 명세서에 없는 정책. Mock은 화면 확인용 **임시값**으로만 동작하며, 확정 전에는 백엔드 규칙으로 쓰지 않는다 |
| 📌 **확정** | 명세서 또는 이번 대화에서 사용자가 결정한 정책 (plan.md 3장 · 7.1, DATA_MODEL 6.9) |

### 0.2 원칙

- **최종 판단은 서버가 한다.** 프론트 검증은 빠른 안내용이며, 서버가 같은 규칙을 다시 검사한다. (FEATURE_SPEC 4.5, 01_auth 5.3)
- **비공개 정보는 응답에서 뺀다.** 화면에서 숨기는 방식이 아니다. (F-13)
- **계산 값은 저장하지 않는다.** 모금액 · 남은 금액 · 달성률 · 펀딩 상태는 조회할 때 서버가 계산한다. (DATA_MODEL 6.6)
- Mock 코드는 "이렇게 동작한다"는 참고 자료다. FastAPI 구현 시 `lib/mock/handlers/*`의 처리 순서와 오류 코드를 기준으로 삼되, 트랜잭션 · 잠금 · 보안은 이 문서의 🔧 항목을 따른다.

## 1. 공통 규칙

### 1.1 인증 · 권한

| 규칙 | 근거 | 구현 위치 |
|---|---|---|
| 로그인하지 않은 사용자는 보호된 화면 · API에 접근할 수 없다 | F-01 | ✅ 프론트(`AuthGuard`), ✅ Mock(`requireUser`) → 🔧 백엔드 JWT 검증 의존성 |
| 생일자 = 펀딩을 만든 사람. 생일자 전용 기능은 `funding.owner_id == 요청자`일 때만 | F-07, 4.1 | ✅ Mock(`assertOwner`) → 🔧 백엔드 |
| 후원자 = 펀딩이 연결된 그룹의 참여자이면서 생일자가 아닌 사람 | F-06, 📌 D-S1-2 | ✅ Mock(`assertSupporter`) → 🔧 백엔드 |
| 펀딩 열람 범위 = 초대받아 참여한 그룹의 펀딩 | 📌 D-S1-2 | ✅ Mock(`canViewFunding`) → 🔧 백엔드 |
| 그룹 관리자 권한과 펀딩 생일자 권한은 구분한다 | 4.1 | ✅ Mock → 🔧 백엔드 |

### 1.2 오류 응답

- 형식: `{ code, message, field_errors?, max_available? }` · 코드와 HTTP 상태는 API_SPEC 1.2.
- 입력 오류는 `VALIDATION` + `field_errors`(필드별 문구). 화면은 입력값을 유지한 채 입력창 아래에 표시한다. (base.md 6.2 입력 규칙)
- 권한 오류(`FORBIDDEN`)와 없음(`NOT_FOUND`)은 화면에서 "접근 권한 없음"으로 보여준다. ✅ 프론트(`AsyncBoundary`)

### 1.3 중복 처리 · 일관성

| 규칙 | 근거 | 구현 위치 |
|---|---|---|
| 같은 요청이 두 번 처리되지 않는다 (후원) | F-08, F-10 | ✅ 프론트(버튼 잠금 · 요청별 키 생성), ✅ Mock(멱등 키 확인) → 🔧 백엔드 UNIQUE 제약 |
| 동시에 여러 요청이 와도 목표 금액을 넘지 않는다 | F-10, 4.5 | 🔧 백엔드 행 잠금 (Mock은 단일 탭이라 재현 불가) |
| 후원과 메시지, 펀딩 삭제와 연결 데이터 삭제는 한 단위로 처리한다 | F-14, 📌 D7 | ✅ Mock(순서대로 처리) → 🔧 백엔드 DB 트랜잭션 |
| 처리 완료된 이월 · 인출 · 정산은 다시 처리할 수 없다 | F-11, F-12 | ✅ Mock → 🔧 백엔드 UNIQUE · 상태 검사 |

### 1.4 시간 기준

- 펀딩 상태와 알림 날짜는 **Asia/Seoul 날짜** 기준으로 서버가 계산한다. 📌 DATA_MODEL 6.0
- 펀딩 상태: 오늘 < 시작일 → `scheduled`, 시작일 ≤ 오늘 ≤ 종료일 → `active`, 오늘 > 종료일 → `ended` (**종료일 당일까지 진행 중**). ✅ Mock(`getFundingStatus`) → 🔧 백엔드

## 9. 프론트 구현 vs 백엔드 구현 요약

| 영역 | ✅ 프론트에 이미 구현 (화면) | ✅ Mock에 임시 구현 → 🔧 백엔드가 다시 구현 | 🔧 백엔드에서만 가능 (새로 구현) |
|---|---|---|---|
| 사용자 관리 | 입력 형식 검증 · 문구, 토큰 보관(유지 여부), 로그인 복귀 경로, 로그아웃 시 캐시 삭제, 취향 폼(추가 저장 · × 삭제) | 필수값 재검증, 이메일 중복, 로그인 인증, 취향 정리(중복 · 개수) | Argon2 해시, JWT 발급 · 만료, 이메일 UNIQUE, 이미지 업로드 |
| 그룹 · 초대 | 관리 버튼 권한별 표시, 링크 복사, 만료 · 비활성 표시, 초대 복귀 흐름 | 관리자 · 참여자 권한, 링크 권한, 만료 판정, 중복 참여 방지, 이동 대상 계산 | 예측 불가 토큰, 복합 PK · UNIQUE, 참여 트랜잭션 |
| 선물 · AI | 필수 4항목 검증, 가격 · 삭제 잠금 표시, 임시 목록, 공통 삭제 모달 | 생일자 권한, 가격 변경 · 삭제 제한, 마지막 선물 보호, 추천 조건 검증 | 행 잠금으로 경쟁 방지, OpenAI 호출 · 응답 검증 |
| 펀딩 | 생성 폼 · 임시 저장, 이월 불러오기, 선물별 달성률 표시, 권한별 타입 분리, 삭제 버튼 잠금 | 모금액 · 달성률 · 상태 계산, 권한별 응답, 삭제 조건 · 연결 데이터 처리, 이월 다시 열기 | 집계 쿼리, 권한별 응답 모델, 삭제 · 생성 트랜잭션, FK 동작 |
| 후원 · 메시지 | 추천 금액 · 직접 입력, 추천 문구, 멱등 키 생성 · 재사용 규칙, 버튼 잠금, 실패 시 입력 유지 | 검증 순서 · 문구, 멱등 처리, 초과 시 최대 금액, 편지함 권한 | **행 잠금 + 트랜잭션(동시 후원)**, 멱등 키 UNIQUE |
| 미달 · 정산 | 선택 · 확인 모달, 미달 처리 기한 안내, 계좌 입력 검증, 모의 정산 표시, 실패 이유 안내 · 재입력, "정산됨" · "정산 진행 중" 배지, 진행 중 자동 새로고침 | 종료 확인, 중복 처리 방지, 정산 금액 계산, 본인 명의 확인, 모의 상태 진행(3초 · 8초), 실패 시 다시 정산 대상, 선물별 정산 상태 응답 | 계좌 암호화, 정산 항목 UNIQUE, 송금 결과에 따른 상태 변경 작업, 7일 경과 미달 알림 작업 |
| 캘린더 · 알림 | 캘린더 · D-day 표시, 빨간 점, 알림 클릭 경로 | 일정 권한, 연결 펀딩 권한, 알림 중복 방지, 일정 삭제 시 알림 삭제 | APScheduler 일일 생성, dedupe UNIQUE |

## 12. 용어

| 용어 | 뜻 |
|---|---|
| 생일자 | 펀딩을 만든 사람 (그 펀딩의 관리자) |
| 후원자 | 펀딩이 연결된 그룹의 참여자로서 후원하는 사람 |
| 멱등 키 (`idempotency_key`) | 같은 후원 요청을 구분하는 값. 같은 키로 다시 보내면 한 번만 처리 |
| 이월 | 목표 미달 모금액을 다음 생일 펀딩의 시작 모금액으로 넘기는 것 |
| 인출 | 목표 미달 모금액을 지금 정산받는 것 |
| Hard Delete | 데이터를 완전히 지움 (복구 불가) |
